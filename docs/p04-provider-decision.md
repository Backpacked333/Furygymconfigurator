## 1. Recommendation and decision strength

**Recommend a portable transactional control plane, immutable private objects, an explicitly authorized delivery boundary, and separately fenced private workers.** Keep all admission, reservations, job transitions, kill state, publication manifests, and reconciliation in the transactional database; neither a CDN, an object bucket, a serverless function's memory, nor a worker volume is the ledger.

**Preferred future provider combination, conditional on the holds in section 9:** managed PostgreSQL on Supabase; private AWS S3 Standard objects in a specifically approved region; CloudFront with origin access control (OAC) and separately enforced viewer authorization; an independently operated control-plane/watchdog service; Modal only as a future private-worker candidate. Keep the existing Vercel frontend unchanged. Hosting the control-plane/watchdog is an unresolved procurement input, not a claim that either Vercel Functions or Modal alone supplies an independent watchdog.

Reasons for this preference:

1. PostgreSQL permits atomic accounting, uniqueness, and fenced publication without tying the domain to a storage SDK. Serializable transactions still require bounded whole-transaction retry handling; default Read Committed alone is not proof of a correct multi-account reservation [P1].
2. AWS documents create-only conditional writes, checksums, version recovery, private origins, and explicit invalidation/deletion semantics [A1–A9]. These are useful for non-overwriting publication and recovery; they do not provide a transaction spanning PostgreSQL and S3.
3. Supabase Storage is the simpler integrated alternative, but its documented S3 compatibility excludes versioning and deleted objects cannot be restored; PostgreSQL backups do not contain object bytes [S3, S4]. Its documented signed-URL cache behavior is also material to revocation [S5].
4. Vercel private Blob and signed URLs are real documented options, not assumed missing features [V2, V4]. Blob would reduce frontend-platform integration work but still needs a separate transactional ledger and independent worker controls. Its regional/CDN pricing and restore/revocation commitments must be established [V1–V6].
5. Modal's existing repository integration is relevant prior art, **not a safe P04 worker adapter**. Default public Web Functions, per-parameter container pools, automatic crash rescheduling, retained inputs, and billing delay need new controls [M1–M8, M10]. No current adapter or provider has been qualified for paid execution.

This preference trades more IAM, contracts, operators, and cross-provider incident handling for explicit object recovery and delivery controls. If jurisdiction requires that all request/control metadata stay in one country, Modal may be unsuitable even with regional containers [M2]. If AWS access or operational ownership cannot be supplied, reconsider the integrated Supabase stack; do not silently relax the safety requirements. No numeric provider score or total-cost claim is justified before traffic, regions, retention, and account plans are known.

### Modal/private-worker evaluation shared by all stacks

**Verified documented capabilities:** container isolation using primitives such as gVisor or microVMs, encrypted transport/storage, and documented retention [M1]; selectable execution regions and separate routing regions [M2]; execution/startup timeouts [M3]; per-function/pool autoscaling bounds [M5]; call cancellation API [M6]; workspace usage budgets and Team/Enterprise environment compute budgets [M7]; opt-in Web Function proxy authentication [M10]; restricted/single-use functions and network blocking options [M11]. None establishes that the existing account or legacy app uses them.

**Retention/residency:** Function inputs/outputs are retained up to 7 days; logs are plan-dependent (documented 1 day Starter, 30 days Team, configurable Enterprise); files in Volumes/Images persist until deletion. Container execution region does not alone constrain data location. Default Function routing is Virginia; inputs/outputs larger than 2 MiB still use `us-east` object storage even with another routing region [M1, M2]. Send bounded opaque context and private object references rather than bulk images through Function results; this is a design mitigation, **not** proof of acceptable residency or zero retention. Required routing modes must be checked against invocation restrictions before choosing `.spawn`.

**Cost and control gaps:** an execution timeout is per attempt, excludes scheduling, and may overrun by seconds. Startup and idle/warm resources have their own costs. Class parameter values have independent container pools. Explicit retries are not the only retries: deployed-app container crashes are documented as retried indefinitely with backoff [M3–M5]. `cancel(terminate_containers=False)` does not request container termination by default; requesting termination can cause other concurrent inputs on that container to be rescheduled [M6]. Therefore setting `retries=0`, `max_containers=1`, or cancelling a Future is not a proof of a global bill/runtime bound.

**Access/recovery:** deploy no public worker endpoint; require authenticated provider invocation plus an application-signed, audience-bound, expiring, byte/runtime/attempt-bounded context tied to the active fence. Isolate the worker app/environment from legacy rendering, avoid multi-input sharing for bounded attempts, and allow only server-selected images/assets/commands. Network blocking is documented, but selective egress needed for heartbeat/object transfer and provider identity behavior require adapter qualification. No broad DB/service-role/provider administrator token in the worker. Modal Volumes are useful worker caches, not the canonical ledger or publication store; volume storage charges can continue up to four days after deletion [M12].

**Unverified and blocking:** precise stopped-host receipts, termination latency ceiling, metering completeness/watermark, budget enforcement latency, orphan enumeration privileges, startup/crash-loop containment, egress restrictions, deletion attestations, paid account/region availability and operational access. Billing reports are Team/Enterprise and may have collection delay [M8]. An independent watchdog must survive the control process and be able to discover and stop orphaned worker resources; no such production service or permission has been verified. If finite upper bounds cannot be established, paid admission must stay disabled rather than inserting an arbitrary margin.

## 4. Portable control-plane and publication obligations

These are **proposed acceptance requirements**, not claims that this documentation lane implemented them. Wire details belong to the shared contracts, not this ADR.

1. **Narrow API:** strict validated v4 `DesignEnvelope` including named presentation and its sole server-allowlisted output profile, plus an idempotency key; no second profile override. Authenticated principal/experiment context stays outside the body. Reject unknown fields, asset URLs, meshes, arbitrary cameras/samples, scripts, callbacks, commands and unrestricted priorities. Use the existing domain parser/identity. Return 200 only for a verified exact identity match, 202 for admitted durable work/status, 422 invalid, authentication/authorization failures as appropriate, and truthful 429/503 for capacity/budget/store failures. A diagnostic cache hit remains explicitly diagnostic, never an approved design image.
2. **Atomic admission:** one transaction checks the persistent kill latch, uniqueness/idempotency, global/experiment/principal budgets and capacity, then writes the job, full worst-case reservation, event log and durable outbox. Record `requested`, `reserved`, `queued` atomically if those are immediate transitions. Reserve integer cost units against immutable policy versions; no browser-controlled budget/profile/priority. Coalescing must preserve authorization isolation and account for incremental delivery/storage interests, not leak another principal's artifact.
3. **Durable execution:** requested → reserved → queued → leased → rendering → publishing → ready; failed/cancelled/expired only when their meaning is proven. Use monotonic fences, lease heartbeat bounded by the original deadline, idempotent transitions, and a retained reconciliation flag/state for uncertain execution. Lease loss, timeout, disconnect or stop request never proves a worker is stopped. Uncertain work retains liabilities and concurrency slots; late/stale workers cannot publish or start an unreserved retry.
4. **Object publication:** use a server-derived immutable key containing a revision/build/request identity and content SHA-256, not a principal ID or caller URL. Upload bounded output into a private staging/quarantine namespace; independently validate diagnostic recipe/provenance, actual bytes, dimensions/type, identity and SHA-256. Verify stored bytes, not just metadata echoed by the worker; never treat ETag as the domain SHA-256. For S3 use create-only conditional writes and explicit checksum facilities [A2, A3]. Keep unverified/staging prefixes inaccessible to the delivery signer.
5. **Publication commit:** after verified immutable storage, one fenced DB transaction writes the manifest/object identity/checksum and ready event/state, rechecking kill/auth/expiry. Object upload and DB commit are **not** a cross-service atomic transaction. If upload succeeds but commit fails, there is an inaccessible orphan, not a ready image; retain storage liability and reconcile it. Duplicate upload/commit retries must verify the same bytes and revision. Missing/corrupt/deleted objects fail closed on reads and never silently regenerate under the old budget.
6. **Delivery:** return only manifest-bound immutable artifacts through an authorized, bounded delivery boundary. No arbitrary CDN transforms may change bytes under that identity. A signed URL is reusable bearer access until its effective expiry/cache behavior ends; it is not one-time authorization or a byte/request quota. A simple direct-CDN signed URL therefore cannot by itself implement strict principal/global delivery budgets.
7. **Export:** a separate explicit export route captures the immutable design revision and bounded output profile; no automatic export/render side effect of viewing, save or share. In P04 it can provide labelled diagnostic artifacts only, with no strict-export/PDF/photorealistic promise. It uses the same admission/publication controls rather than a privileged budget bypass.

For the preferred stack, begin any future qualification with an authenticated **no-store delivery relay** that checks persisted budgets and streams under actual byte/deadline/concurrency caps. Private CloudFront/S3 may be behind that relay, with signer credentials never exposed to the browser. Direct viewer CDN delivery stays on hold until an edge authorization/metering design can enforce aggregate limits on repeated downloads, range requests and already-open streams, or the user explicitly accepts a separately bounded delivery-risk model. Do not count a future edge feature as implemented. Regional relay hosting, egress and denial-of-service overhead must themselves be budgeted.

## 5. Cost model and non-negotiable kill semantics

Provider quotas and advertised free credits are secondary guardrails, not authorization to spend. No production dollar limit is selected here. Keep the P04 synthetic ledger and all prior budgets intact.

A future reservation needs a finite conservative bound for each admitted miss, plus incremental reservations for cache-hit delivery and retention:

```text
R = attempts × (startup + maximum execution + bounded retry overhead)
  + allocated warm/idle tail + shutdown/termination tail
  + bounded object puts/gets/verifications and delivery bytes/requests
  + object, staging, version/backup retention and deletion tail
  + allocated API/DB/watchdog/log/other fixed costs
  + delayed-meter and price/currency/tax safety margin
```

Every term is cost in the ledger's integer currency/unit model, derived from explicit maximum usage × approved regional rates. Runtime includes CPU, memory and GPU, not GPU alone. `attempts` includes provider-visible rescheduling liabilities, not only application retry counters. Do not double-count a tail already included in an attempt; document attribution for shared/warm costs. Fixed monthly infrastructure needs its own experiment/global reservation before admissions, not a claim that each job's marginal cost covers the bill. If provider rescheduling or termination is unbounded/unknown, no finite reservation is defensible: **fail closed**.

This document does not claim these tests passed. Real-provider destructive/paid kill experiments are not authorized in P04.

## 6. Retention, signed-URL revocation and recovery

- Establish distinct approved lifetimes for design/private context, original bytes, derivatives, exports, incomplete uploads, job/idempotency rows, audit events, spend balances, provider logs, versions and backups. Storage cleanup cannot reset spent budgets, delete unresolved liabilities, or reopen old idempotency keys without an explicit policy. Keep minimal non-sensitive accounting/tombstones for their required lifetime; do not retain full design bodies indefinitely merely to preserve balances.
- Separate **application revocation**, **edge invalidation**, **browser cache expiry**, **origin deletion**, **version/backup expiry**, and **physical/provider erasure assurance**. They are different events with different receipts. Already-downloaded copies cannot be remotely recalled. Do not promise immediate erasure from a successful delete HTTP response.
- Supabase's signed-token expiry caveat is explicitly documented [S5]. Vercel's signing defaults must be narrowed to the exact pathname, GET operation and short lifetime; no per-token immediate revocation guarantee was established [V4]. S3 presigns may be reused and expire with underlying credentials; broadly revoking a signing role affects other URLs [A6]. CloudFront URL expiry is checked at request time, not continuously through an existing stream [A8]. None is an aggregate delivery cap.
- A CDN invalidation must be paired with origin denial/deletion and stopped future signing; otherwise an authorized request can repopulate the cache [A9]. For private output, default browser responses to `private, no-store`; do not apply the legacy `/stills` one-year immutable browser policy. Immutable **object identity** does not require irrevocable **access caching**.
- S3 versioning improves recoverability but prolongs retention/cost. Delete markers do not remove versions, lifecycle acts asynchronously, Object Lock and replication status can defer expiry [A4, A5]. Supabase PostgreSQL backups contain Storage metadata but not deleted bytes [S3]. Vercel backup/physical-erasure guarantees and Modal provider-internal deletion propagation remain contractual unknowns. Delete work must cover worker caches/images/log retention where relevant, not just the public URL.
- On ordinary restart, replay the durable outbox and fenced job state, do not reset policy or balances. On **database restore/PITR**, freeze all admission: an older backup may omit spent money, leases, kills and externally uploaded objects. Reconcile provider resource inventories, object versions/manifests, external usage receipts and deletion tombstones before rebuilding monotonic liability totals and the kill epoch. If the missing interval cannot be reconstructed, retain the conservative bound and remain unavailable; never treat a restored low balance as refunded spend. A paid recovery design needs independently retained accounting/kill evidence and an approved RPO/RTO; this review did not establish those facilities.
